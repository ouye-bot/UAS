# R1 实用化主线 · 实施计划（2026-09-21，接落地实用化改进路线）

> 架构定谳（本批最关键事实）：`zkc verify` 现行实现以 spec **重装配全电路（含秘密见证）**
> ——若按 B4 接线把 spec 交服务端，飞手秘密必须出设备，隐私架构不成立；且 `zkc verify`
> 依赖 prove 侧 verifier_param（Task 6 深坑），B4 worker 的替身测试掩盖了此缺口。
> 本批根治：**验证面改为「实例驱动」**——服务端只见公开实例，秘密永不出设备。

## R1-1a zksvc：实例驱动验证面
1. `prove_pipeline` 落 `instances.json`（`{"instances": ["<BE32 hex>" × N]}`，`fe_be32`）。
2. 新库函数 `verify_instances(proof, vp, instances_json, expected)`：
   env `FZ_AUTH_CANONICAL_SPEC` 装配 canonical 电路一次（advice 丢弃——信息面结构
   对同档语句恒等），按索引核对期望实例：19=ctx_tag(challenge)、20=pred_id_fp(pred 串)、
   21=T(t_epoch)、22=θ(required_level)、23=fold_words_be(rev_root)、24=class_id——
   不符=结构化 FAIL；再走既有 verify 管线（info+instances+vp+proof）。
3. CLI 增 `verify-instances --instances --proof --vp`。
4. 测试：golden spec 出证→instances→verify-instances OK；篡改任一受检实例→FAIL
   （集成档 #[ignore]+单元 fail 路径）。

## R1-1b backend：绑定面+受理一致性+worker 换代
1. `GET /authz/binding?class_id&plan_hash_hex&nonce_hex`：政策查表（fail-closed）→
   challenge=HMAC-SM3(服务密钥, plan|nonce)[:32]（确定性/不可伪造/免存储）、
   pred_id 串=`{plan}|{nonce}|{policy_version}`、t_epoch=now、alt_max/required_level。
2. `GET /ra/pubkey`；`GET /ra/revocation/witness?holder_pk_hex=`（key=pk′.x，
   `non_membership_witness`——smt.py 现成）。
3. `ApplyIn` 换代：`proof_hex/spec_json` → `case_id + t_start + t_end`（桥接把
   proof/verifier_param/instances 写入共享 cases/{case_id}/——同机演示经共享目录，
   远程部署的 vp 传输=生产缺口如实登记）。
4. `admission_gate` 增**实例一致性校验**（毫秒级，先于排队）：调 zkc verify-instances
   前由 Python 校验期望（ctx_tag hex/pred_id hex/θ/T/class 的域元素形态经 SM3 mod p
   折算——以 ctx_tag_vectors.json 跨语言锚钉死一致性）+ token 窗口校验。
5. worker：`zkc_verify(case_dir)` 改调 `verify-instances`（B4 替身测试同步换代）。

## R1-1c bridge：实时出证服务
- `POST /prove/start`（入参=申请参数+本机登记材料——web→localhost 桥接，不出设备）：
  取 /ra/pubkey、/ra/revocation/witness、/authz/binding → 组装 JobSpec 临时文件 →
  `zkc prove` 子进程 → 产物迁 cases/{case_id}/。
- `GET /prove/task/{id}`：状态机 + 失败原因。

## R1-2 web：申请屏真实流程
- 提交=桥接出证（真实进度）→ 自动 apply（case_id）→ 回执轮询（worker 秒级 ready）。
- 占位/文件模式整体删除（产品面禁占位）。

## 顺序
A（zksvc）→ B（backend）→ C（bridge）→ D（web）→ E 端到端实测（真出证+真验证+取件
+解锁）→ 判决行+文档+commit。共享仓改动随 A 走 vendor 换代流程。
