## 1. 服务器规格要求

### 1.1 硬件

| 项 | 建议 | 硬底线 | 依据（全部在案实测） |
|---|---|---|---|
| CPU | **≥12 vCPU**（④代机型同款 12C） | 4 vCPU（须加测对照行并如实标注） | 测量口径 RAYON=12；R1 扫参 12 线程服务器最优；④代 AUTH@RAYON8 28.13s vs RAYON12 25.14s——核数不足时口径失真 |
| 内存 | **32 GiB**（46 GiB 对齐④代机型最优） | 16 GiB（构建须 `-j` 降档） | ⑦代 prove 峰值 RSS **≈7.5GB**（RAYON=12，2026-10-06 实测；内存准入线 8.5GB）+ AUTH pp 工件 **4.26GB** 读写瞬态（跨证明缓存尺寸门实测）+ release 构建并行峰值（`-j8` 数 GB 级）。16GiB 机能跑 prove（7.5GB 峰 + OS），构建峰值与页缓存是主要风险 → `-j2~4` 降档 |
| 磁盘 | **≥40 GB 空闲** | 24 GB | release 构建 target 3~6GB + 每发判决件（proof+vp+instances+verdict）约 40~50MB×6 发 + 系统与页缓存余量。写满=测量窗报废 |
| 架构/OS | Linux x86_64；④代=Alibaba Cloud Linux 4 | 任意现代 glibc 发行版 | 仅需 `python3 ≥3.8`（脚本零第三方依赖）+ `git` + `gcc`（mimalloc/libmimalloc-sys 的 C 编译与链接） |

### 1.2 软件依赖与版本钉定

| 面 | 钉定 | 说明 |
|---|---|---|
| 工具链 | **nightly-2026-05-26**（x86_64-unknown-linux-gnu） | ④代 B1/B2 基线窗同款（2026-09-23 窗同钉）；组件三件套 rustc/cargo/rust-std。🔴 `zksvc/rust-toolchain.toml` 钉的是 `nightly-x86_64-pc-windows-msvc`（Windows 通道，Linux 装不到）——服务器一律用 `RUSTUP_TOOLCHAIN=nightly-2026-05-26` 环境覆盖（④代同法），**勿改 rust-toolchain.toml 本体** |

| 测量脚本 | `python3 ≥3.8` 标准库 | `scripts/server_bench.py` 零第三方依赖 |

### 1.3 工具链离线安装（④代配方复用）

```bash
# 本地取得三件套（static.rust-lang.org dist 的 2026-05-26 日期目录）后 SFTP 直传：
#   rustc-nightly-x86_64-unknown-linux-gnu.tar.xz
#   cargo-nightly-x86_64-unknown-linux-gnu.tar.xz
#   rust-std-nightly-x86_64-unknown-linux-gnu.tar.xz
# 服务器侧逐件解包 install.sh --prefix（④代 2026-09-27 窗同法）：
for c in rustc cargo rust-std; do
  tar xf ${c}-nightly-x86_64-unknown-linux-gnu.tar.xz
  ./${c}-nightly-x86_64-unknown-linux-gnu/install.sh --prefix=$HOME/rust-nightly-0526
done
export PATH=$HOME/rust-nightly-0526/bin:$PATH
export RUSTUP_TOOLCHAIN=nightly-2026-05-26   # 覆盖 windows 通道钉（不改 rust-toolchain.toml）
rustc --version && cargo --version            # 自检段会复核并记入机器画像
```

（若服务器可直连外网，`rustup toolchain install nightly-2026-05-26 --profile minimal` 一条等价；
但内网/安全组场景走三件套。工具链版本漂移的影响见 §6.3。）

### 3.2 构建复现性门（本套件的核心防线）

期望指纹 **SM3(4201a82|b05df9d8e2d5f39fb4d92b19d47379c86c0d40159e9fd39a1c9c77455b9b4985)**
（⑦代现行＝2026-10-11 2.1 批 MANIFEST 151 文件态；三源在案一致：
`zksvc/build_manifest.json` aggregate_sm3＝`backend/scripts/crypto_audit.py`
PIN_LOCAL_EXPECTED＝`zksvc/tests/auth_golden_vector.json` zk_pin_fingerprint）。

门分两面，**任一面不符即中止**（防"服务器构建产物与判决件不一致 → 测量有效性翻车"）：

1. **源面**（构建前后都可跑）：脚本按 `pin_fingerprint.rs` 同构式复算——MANIFEST
   file_count 自洽 + 151 文件逐个存在性/字节数/SM3 重算 + hex 串聚合，期望值三源核对。
   这面在本地已对既有 vendor 树实跑 PASS（§7）。
2. **判决件面**（构建后每发 prove）：stdout 与 verdict.json `zk_pin_fingerprint` 双读，
   不等于期望指纹即中止；并核对 pcs tag＝`il=1/dd=0/st=0`、AUTH proof 尺寸＝黄金
   **16,063,712B**、AUTH 公开实例 26 条与黄金向量**逐位一致**、TRAIL 实例数＝8。

说明：证明字节本身**不跨次复现**（mask=on OsRng 每证新鲜——R1 批在案结论），所以
对拍锚＝尺寸+指纹+公开实例三元，`proof_sm3` 仅记录不比对。黄金向量差分对拍世界
（钉盐+MASK_OFF）是 cargo test 专用档，**不**用于本测量（production 准入拒绝该组合）。

### 3.3 执行序列

`full` 子命令依序执行，红即中止：①机器画像 → ②口径门（禁设 env 清零+准入门禁注入）→

⑤AUTH canonical prove ×3 → ⑥TRAIL canonical prove ×3 → 中位数与 ≤60s 门判定 →

## 4. ≤60s 硬门判定规则（预写）

- **判定对象**：AUTH canonical prove 中位数（N=3），数据源 verdict.json `prove_s`
  （与④代 25.14s 同口径同源）。
- **规则**：中位 ≤60s → **PASS**；余量倍数＝60 ÷ 中位（④代口径"余量近 2.4×"同式）。
  结果件自动判定并写入 bench_results.md 的回填块。
- **FAIL 处置**：照实入档、勿弃测量勿重跑挑数——硬门未达本身是有效测量结论，处置
  归队长拍板（候选：性能优化立项 / 演示口径降档声明）。
- **TRAIL 无硬门**：记录 prove/verify 中位，对照④代 15.10s / 0.21s 与本机 12.3s
  （2026-10-07 实测）即判读；TRAIL ⑦代 proof 尺寸是**新数字**（档案现存值 16,249,632B
  为④代口径），一并回填。
- 次口径：`total`（含装配/setup/preprocess）一并记录供参考，硬门只看 prove（与现行
  口径总表行一致）。

## 6. 常见翻车预案

1. **构建 OOM**（链接期/高并发期）：`python3 scripts/server_bench.py full --build-jobs 2`
   降档（④代 R3-3.1 窗 -j2 增量构建 87s 先例）；16GiB 机建议直接 `-j2~4`；判读
   `dmesg | grep -i oom`。证明段内存（峰值 ~7.5GB）与构建峰值不叠加——构建完成后
   prove 单发跑，无需额外腾挪。
2. **指纹门红**：①传输损坏 → 重传对应包，落地先 `git bundle verify`；②换行污染 →
   手工 tar/网盘中转是主嫌，改走 git bundle/archive（`core.autocrlf=false` 教训①）；
   ③拿错代际 bundle（⑤⑥⑦代 MANIFEST 各异，file_count 151＝⑦代态）→ 核对
   build_manifest.json 的 aggregate_sm3 与 §3.2 期望值；④三源期望值自身漂移（理论上
   不应发生——本地已三源核对 PASS）→ 先对账 crypto_audit PIN_LOCAL_EXPECTED 再动。
3. **工具链版本漂移/钉定失效**：`error: toolchain 'nightly-x86_64-pc-windows-msvc'
   is not installed` ＝ rust-toolchain.toml 的 windows 钉生效 → `export
   RUSTUP_TOOLCHAIN=nightly-2026-05-26`（勿改 toml 本体）；组件缺失 → §1.3 三件套补装。
   版本对不上日只有时延口径风险（④代两窗曾并存 05-26/08-25 两钉的先例）——判决行
   必须自述工具链；**跨工具链版本不做时延直比**，宁可补装 05-26 重测。
4. **prove FAIL/panic**（如 distinct-x、batch_open 槽断言）：⑦代已知双缺陷已于
   2026-10-07 根修（案卷 a90cc307/d6a7fe3c 复跑 OK 在案）；复现即**新缺陷**——停手，
   保留 stdout/verdict.json/机器画像留档上报，**严禁改码重测**（改码＝换代＝本窗作废）。
5. **尺寸门/实例门红**（AUTH ≠16,063,712B 或实例 ≠26 逐位）：几乎必为 vendor/spec
   非同代（黄金向量 v7＝⑦代）或指纹门被绕过——本套件门序设计使其不可绕过；核对
   bundle 代际后重来。
6. **proof_sm3 每发都不同**：不是翻车——mask=on OsRng 每证新鲜，证明字节本不跨次
   复现（§3.2 三元锚才是门）；不要试图"修"它，更不要设 MASK_OFF 去凑一致（口径门
   会先拦）。
7. **磁盘写满**：构建 target 3~6GB＋判决件 6 发 ≈300MB；预留 40GB。满即清
   `zksvc/target` 重来（构建幂等）。
8. **核数 <12**：维持 RAYON=12 同口径主判决并如实标注超订；可选加测
   `RAYON_NUM_THREADS=<核数>` 对照行（脚本外手工一发即可），对照行不回填主判决行。
9. **cargo 离线拉源失败**（serde_json 等走 index 失败）：`.cargo/config.toml` 未生成
   或 vendor-reg 未落位——脚本自动复制 config-offline-full.toml（🔴必须 full 版，
   手抄截断版＝④代首踩雷）；确认 `zksvc/vendor-reg/` 非空。
