# 三大测试体系设计方案（2026-10-02 · 密码技术 / 安全防御链 / 性能）

> 来源：三路独立解剖「密信护盾」三大测试脚本（crypto 69KB/security-fault-tolerance
> 54KB/performance 46KB，含 14 份真实运行报告）→ 批判出 40+ 条弱点 → 在其骨架上
> 为飞证重新设计。原则：**不是从零造测试**（飞证已有 pytest 278+e2e 62+角色 30+S1
> 46+桥 32），而是把散布的防御与性能数据整合成三大可一键运行、出统一报告、
> 攻击即失败的对抗性套件。

## 一、从密信护盾提炼的十条铁律（每条都有其行号级事故证据）

1. **测试绝不携带任何豁免头/旁路标记**（其 `x-test-mode` 头跳过整条安全链——测试亲手绕过被测对象）；并设元测试：外部携带测试标记必须被拒。
2. **官方向量对拍是正确性之锚**——其零向量对拍（"库和自己对拍"）是最大短板；飞证三语言共享向量源保留并强化。
3. **404 一律判环境错误并中止整套**（其端点改名后 404 被记 passed，六份报告从全绿到哑弹过半而测试无法自知）。
4. **knownIssue 不设软通道**（其已知漏洞登记后永不计失败，套件永绿）；用 xfail(strict) 保持红灯压力。
5. **退出码与结论联动**（其 64 项全挂也 exit 0）。
6. **异常≠通过**：须断言异常类型与 fail-closed 语义（其"抛任意异常记 passed"）。
7. **单变量改动**：测时间窗/nonce 格式必须保持签名有效（其改字段发生在签名后，401 来自签名失配而非被测逻辑）。
8. **资源观测必须指向被测服务**（其"资源监控"监控的是压测客户端自己）。
9. **报告强制环境快照**（其四轮报告 QPS 漂移 5.4 倍无法归因；无 git/版本/环境）。
10. **测试数据零污染**：临时目录/独立 schema，禁触生产库，报告脱敏（其报告泄漏有效 TOTP 令牌与密文前缀；直写生产数据文件）。

## 二、统一报告 schema（三脚本共用，横向对比的数据格式基础）

```json
{
  "schema_version": 1,
  "run_id": "<uuid>",
  "suite": "crypto | security_chain | performance",
  "env": {"git_commit": "...", "cpu": "...", "cores": 0, "ram_gb": 0, "os": "...",
           "python": "...", "rust": "...", "node": "...", "circuit": {"name": "...",
           "constraints": 19578, "proof_bytes": 22675632},
           "prove_max_concurrent": 1, "chain_mode": "real", "timestamp": "..."},
  "summary": {"total": 0, "passed": 0, "failed": 0, "xfail": 0, "pass_rate": 0.0,
               "duration_s": 0.0, "verdict": "success|failed"},
  "modules": {"<模块名>": {"passed": 0, "total": 0, "items": [
      {"name": "...", "verdict": "pass|fail|xfail|environment_error",
       "expected": "...", "actual": "...", "defense_ref": "app/xxx.py:NN",
       "attack_success": false, "latency_ms": null, "detail": {...}}]}},
  "baseline_refs": {"<指标>": {"value": 0, "source": "docs/性能档案.md#节"}}
}
```

硬规则：verdict 枚举含 `environment_error`（404/连接拒绝→中止整套）；`attack_success=true`
即整体 failed；敏感物（令牌/密文/私钥）禁止入报告；每条负例挂 `defense_ref`（防线代码位置）。

## 三、三大脚本设计

### 3.1 crypto_audit.py —— 密码技术审计（backend/scripts/）

定位：算法正确性之上测**协议与生命周期**。模块：

| 模块 | 内容 | 与现有 278 pytest 的关系 |
|---|---|---|
| C1 向量对拍 | SM2/SM3/SM4/HMAC 三语言共享向量全量回放（Python 侧） | 已有，纳入报告化 |
| C2 KEK 信封版本矩阵 | v3 正路径+v1/v2 旧版显式拒绝（不兼容即拒）+AAD 三处篡改+跨账户隔离 | 部分已有，补版本矩阵 |
| C3 电路边界×漏洞回归矩阵 | 边界值（==上限/</负/超界/非布尔）×约束族（RangeCheck/Bool/时间门/链头钉）×历史漏洞回归（每次电路批次的负例带 circuit_ref 登记）——密信护盾最强形态的升级版 | 电路负例已有（gate 专属断言），补登记与报告化 |
| C4 嫁接拒绝 | 换电路 spec/换 vkey/换黄金向量的证明提交必拒（电路指纹 pin 面实弹） | 新增 |
| C5 密钥生命周期 | 出示钥一次性（同子凭证无二钥匙）、KEK 密封解封回环、登出焚毁、吊销后重签拒绝 | 部分已有（e2e 2.1b/2.4/4.9），收拢 |
| C6 双控与签名链 | 双签缺一拒/篡改拒/乱序拒/重签 pk′ 互异 | 已有，纳入报告化 |
| C7 恒时性护栏 | SM2 验签/KEK 解封的均值-方差抽样（正确 vs 错误输入的时延分布无显著差异） | 新增（双方共同盲区） |

### 3.2 security_chain.py —— 安全防御链实弹（backend/scripts/）

定位：把飞证 12 环节防御链串成**环节×攻击形态**实弹矩阵，任一攻击成功即整体失败。
每条负例=「攻击动作→断言被拦→**断言审计痕迹存在**」双段（密信护盾完全没有后半段）。

| 环节 | 实弹项（含现状缺口标记） |
|---|---|
| S1 会话隔离 | 三角色×三面 403 全遍历（已有 30 实弹，报告化）+**前端路由层自动化**（补） |
| S2 挑战+限速 | 挑战重放拒+**429 限流实弹**（10 连发触发→429→窗口后恢复——现有体系从未打过的活防线） |
| S3 双控 | 缺一拒/坏签拒/篡改拒 + **并发双 approve 竞态**（双线程同发，恰一成功——补） |
| S4 令牌一次性 | token_used 拒二次 ARM + **双击竞态**（并发双 ARM，恰一次成功——补） |
| S5 围栏 fail-closed | 篡改 alt_max 拒+错 plan 拒（已有）+**围栏参数写入后 PARAM_VALUE 确认缺在**的故障形态（补） |
| S6 nonce 烧毁 | 链级重放 409 + **并发重放竞态** + **断链时烧毁语义**（链停后受理应 fail-closed——补） |
| S7 电路指纹 | pin_mismatch 409 实弹（改本地指纹→受理拒——已有仪式，实弹化） |
| S8 撤销三层 | 按人/传播/签发预检（已有）+ **撤销后 worker 重启仍生效**（补） |
| S9 受理门控五步 | 逐位核对 + **五步乱序/跳步**（缺步提交必拒——补） |
| S10 worker 容错 | **worker 杀进程→任务残留→重启恢复**（execute_failed 语义实弹——补） |
| S11 启动守卫 | 纪元漂移自愈（已有 test_ra_align，真链实弹化） |
| S12 故障注入专项 | **断链（wsl 桥停）→后端受理 fail-closed；恢复→自动重连**（新环节） |

### 3.3 perf_suite.py —— 性能测试（backend/scripts/）

定位：飞证的真差异化=**分钟级大电路出证+串行闸**（密信护盾是毫秒级小电路，其体系完全没有并发出证形态）。核心模块：

| 模块 | 内容 | 口径 |
|---|---|---|
| P1 串行闸并发扫描（核心） | FZ_PROVE_MAX_CONCURRENT=1/2/4 三档：每档 N 次出证，吞吐（证/分钟）×P95 端到端×排队时延×峰值 RSS 四元组 | 预热 1 次丢弃；提交-完成两端打点；排队与服务时延分列 |
| P2 受理面吞吐 | FastAPI 提交/查询/轮询端点，开环恒定到达率+闭环两种形态，**含 429 专项与豁免对照**（密信护盾 W2 反例的正面做） | P50/95/99+stddev；错误样本剥离单列 |
| P3 密码操作微基准 | SM2 签验/SM3/SM4/KEK 解封/derive_auth_r——**输入规模梯度 1K/10K/100K**（杜绝其 SM3 10KB 吞吐反低于 1KB 20 倍而无人解释的异变） | Rust 侧复用 bench_b0.py 思路+报告化 |
| P4 链上写面 | 提交→确认延迟分布（P50/95/99）、批量 N 笔 TPS、国密签名开销单列（密信护盾链上面全缺） | 真链档 |
| P5 端到端业务流 | 注册→出证→受理→ARM→飞行→封链→审计，每步打点 n≥10，**串行闸占比分解** | S1 的性能化形态 |
| P6 服务端资源观测 | psutil 采样**被测服务进程**（backend/worker/zkc）CPU/RSS 1s 粒度——密信护盾 W1 反例的正面做；19.8GB 下最大安全并发数结论 | 采样器随 P1 运行 |

## 四、横向对比规划（诚实版）

1. **对比对象与口径**：
   - 密信护盾（唯一有完整实测数据的参照）：可对比维度=API 受理吞吐（其 QPS 105~573 同机自压）、200 并发读 p95（46~98ms）、小电路 ZKP 出证/验证（90~141ms/9~18ms）。**诚实标注**：双方电路规模差 3 个数量级、环境不同（其 Node/单机自压无环境快照），只做"维度存在性+量级"对比，不做精确数字对比。
   - 飞证自身演进（最硬的对比轴）：电路五代（104,287→44,383→~38.2K→20,102→19,578 约束）、proof 453MB→22.7MB（交织）、vp 2.3GB→5.84MB、验证 11.2s→4.1s、ARM 45s→14s→4s——每代有同机对拍判决行，这是"优化有效性"的可复现对比。
   - 第三方同类系统（UOM/Zcash/长安链等）：本轮调研代理未获取到足量可引用数据（已按队长指示停止），对比表预留结构、标注"待补充公开数据"；不编造。
2. **对比表形态**（进答辩材料）：维度 | 飞证实测（判决行引用） | 参照值 | 口径差异声明——三列制，永不裸比数字。
