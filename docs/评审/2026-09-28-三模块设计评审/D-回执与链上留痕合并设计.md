# 「飞证」⑤回执查询 × ⑥链上留痕 合并可行性独立分析与设计规划

## 一、现状与价值重审

**两页的技术事实。** 回执页是单输入单按钮的极简屏（ReceiptView.vue:31-60），消费公开端点 `GET /authz/receipt/{code}`（authz/router.py:291-296，无任何身份依赖），服务端仅返回 `status` + `token_cipher_hex`（service.py:317-325）——回执码就是唯一凭据，D19“回执表零身份列”在数据面成立。链上留痕页是四板块公示面（链状态/授权记录/检查点/令状，ChainView.vue:148-270），`/chain/panel` 与 `/chain/record/{id}` 均无认证（panel.py:130、173），注释明写“零身份面”（panel.py:8），且带链上原文逐位对账（ChainView.vue:183-187）与本机复验材料五件下载（ChainView.vue:203-216）。

**价值兑现裁定：留痕页已兑现，回执页只兑现了一半。**
- 留痕页对三类受众全部兑现：飞手（本机案卷 `fzLastCaseId` 匹配下载复验材料，ChainView.vue:99-111）、评委（“链上原文核验=一致”机器判定+零身份字段可视对账）、监管/第三方（无守卫可直达，router.ts:20 无 `requiresCred`）。此前评审 P0-2（本机材料区不可达）已以身份域持久键修复（material.ts:65）。
- 回执页的**头牌价值“跨设备查询”在当前实现下是断的**：两处文案宣称“换设备可查”（ReceiptView.vue:36）与“凭此码可在任意设备查询进度”（ApplyView.vue:524），但路由守卫给 `/receipt` 挂了 `requiresCred: true`（router.ts:19）——新设备无 `fzCred` 一律弹回登录页（router.ts:25-30）。D19 唯一 UI 证物恰恰在其宣称的核心能力上不可达，评委拿自己手机验证演示时必落空。这是“回执页功能单一所以想合并”直觉背后的真实病灶：**不是页窄，而是价值没兑现**。另同设备场景它与申请页自带轮询高度重叠（ApplyView.vue:249-293），独立价值只剩“会话丢失后/异地查状态”。
- 回执码的消费链横跨三屏：申请页产生并落 `fzLastReceipt`（ApplyView.vue:289）、回执页查状态、飞行页取件解密（FlightView.vue:116-121）——三屏各取端点的一个切面，分工本就清晰。

**合并直觉的正确成分**是六屏导航略胀；**错误成分**是把“信息面窄”等同于“可归并”，忽视了两页在信任模型上正交：回执=私有能力凭证驱动的瞬态工作流状态，留痕=零凭据的永久公共公示。A 报告四.3 已给“保留”意见（A-前端产品工程师评审报告.md：56），我复核后认同其结论，但理由需补强——它没指出路由守卫矛盾这一硬伤。

## 二、方案对比

**方案一：合并为「查询与公示」单页（六屏变五屏）**。受众动线：公示读者与持码飞手共用一 URL。隐私性质处理：整页须随留痕页去守卫（留痕必须无凭据），私有码输入区从此坐在公开页面上——演示机上评委围观/公用 kiosk 场景下诱导输码，观感与安全双降。对 D19 叙事：唯一证物降格为公示页里的一个输入框，"只凭一个随机码、零身份列”的独立展台消失。实现改动面：router.ts 改路由+重定向（~12 行）、新增 ReceiptQueryCard 组件（~55 行）、ChainView 加 Tab 骨架（~20 行）、删 ReceiptView（−62 行），合计 4 文件 ±90 行，另手测清单 ⑤⑥ 合写、说明书口径重写。风险：私有/公开两种信任级同页；e2e 5/6 段（e2e_frontend_api.py:332-354）API 不变但语义标签失配。**收益仅省一个导航位（App.vue 横导航六项容量充裕，App.vue:107-118），成本是叙事稀释+双页重测，ROI 为负。** 顺带一提：合并后确会“重新符合”说明书 §7.3 的五屏旧口径（MEMORY：394），但第六屏是 S4 已入档的演进（MEMORY：400），文档反正要同步，这不成其为理由。

**方案二：不合并页面，回执查询以组件嵌入留痕页，导航保持**。同页双入口并存，导航不减反增冗余面；公开页面上照样出现输码区，方案一的隐私缺点照单全收，还多了两处状态同步。劣于方案一，否决。

**方案三（推荐，自创）：不合并，修复回执页的价值兑现缺口**。三处小改：①router.ts:19 删 `requiresCred`——该端点数据面本就零身份、回执码即凭据（红队 A1 穷举已被限流拒绝，MEMORY：415），去守卫后跨设备宣称成真，评委可当场用手机凭码查询，D19 证物从“文案宣称”升格为“可现场复现"；②文案小修：failed 态人话化（ReceiptView.vue:12-17 现返回英文原文 "failed"）、页内标题与导航名统一（router.ts:19 “回执查询” vs ReceiptView.vue:34 “申请进度查询”，A 报告 P2 已列）、删死导入 randHex（ReceiptView.vue:5）；③可选单向互链：回执页结果区加“公开公示见「链上留痕」”——**方向必须单向**：回执→链上安全（目标公开），链上→回执禁止（在公开机器上诱导输私有码是反面设计）。实现改动 ~6 行、2 文件。

## 三、推荐方案与页面结构草图

**裁定：采纳方案三，否决合并。** 判据回到受众与信息性质：留痕页回答“这个系统发生过什么、任何人如何独立核验”（永久、公开、证据面），回执页回答“我的这次申请过了没有”（瞬态、凭码、工作流面）。二者唯一的公共点是“都查状态”，这不足以抵消信任模型正交带来的同页成本。保留分立还守住一个精巧的既有设计：回执响应不含 authId，回执面与链上面**设计性不可关联**，关联只发生在取件时凭会话钥解密之后——合并页会在视觉上暗示二者天然可对账，反而伤害叙事。

若队长仍决意合并，方案一草图（降级备选）：

```
/chain「查询与公示」（无守卫）
├─ Tab A 公示核验（默认）：现 ChainView 四板块原样
└─ Tab B 凭码查询：ReceiptQueryCard（码输入→状态/密文摘要→
   "取件请回出证设备"提示）；Tab 标题必须写明"私有·凭回执码"
```

方案三下回执页目标态：无守卫直达 → 输码（占位符即隐私宣言“仅回执码——不需要任何身份信息”，ReceiptView.vue:39）→ 状态标签+密文摘要 → 结果区脚注含单向互链与取件指引。页面窄是 D19 的美学而非缺陷：披露面最小化。

## 五、风险与开放问题
