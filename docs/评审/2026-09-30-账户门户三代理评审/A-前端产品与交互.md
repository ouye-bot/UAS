## 一、总评

这一层的**产品语言进步是实质性的**：四拍协同生命周期、立案自动化预填、双控卡
"让批准人明白为什么"、诚实拒绝文化延续——设计方案的三个意图（一个前门/令牌退役/
双控工作流）在 UI 面全部有实物可指，且旧批 P0 两项（/prove 前缀、case_id 持久化）
经实测确认已修。但本轮实测揪出了一个**比上轮 TRAIL 前缀更重的演示级断点**：live 栈
审计收件箱 20 条线索**全部是死线索**（目标授权在 RA 库无记录，立案 100% 被拒），
旗舰双控动线在当前数据态下从 UI 走不通；外加三处新层自伤——审计台步进器样式漏
共享化（渲染为裸文本）、批准/驳回的交互安全缺一道闸（批准无确认、驳回理由共享
ref 串卡）、TrailView 出证等待标签把 `{{ windowSel }}` 字面渲染。整体定性：
**骨架与语义是三批交付里最好的一版，但"最后一公里的数据态与状态机收尾"仍未过
浏览器级回归关**——收件箱数据一致性、僵尸 approved 恢复、半途注册死端，全是
API 绿测掩盖的 UI/数据面缺陷（与 R2-b/TRAIL 前缀同族第四案）。

## 二、做得出色的（挂证据）

1. **双控卡"明白为什么"是真交付**（F-③"依据丢弃"硬伤的 UI 修复）：机构台待批卡
   完整呈现依据原文/审计理由/目标/令状哈希/发函人指纹/请求指纹
   （AdminView.vue:209-216），实测截图 s6_admin_full.png 逐项可见；匿名令状的
   执行失败文案直接说人话——"该令状未指定目标授权编号——自动执行不可达，请走
   带凭证的重新立案（可重试）"（live 实测，collab 执行错误透传）。批准人拿着
   卡片能向评委讲清"我为什么批"，这是同类作品少见的。
2. **诚实拒绝文化在账户层延续**：错密码登录实测 DenyBox 给出
   `bad_password 密码错误（密封件解封失败）`（本地 AEAD 判定，服务端不参与——
   宣称与行为一致，auth.ts:203-207）；同名重注册 `username_taken 用户名已被占用`
   （实测）；注册密码规范五条实时清单（实测弱密码"12345678"显示 ✗含字母/✗非常见
   弱密码，LoginView.vue:222-226 + enroll.ts:90-109，含黑名单与"与用户名不同"）。
3. **注册向导的密码学可感知做得对**：第一步明说"密钥在本机生成，以密码密封后
   上传——服务器只有密封件"（LoginView.vue:217）；第二步显式标注"这是『上链
   注册』发生的时刻"（:238-241）——把设计方案 §2.2 的时点之问变成了用户可读的
   叙事；身份证脱敏摘要（slice(0,4)+********+slice(14)，:258）细节到位。
4. **切页修复批是实打实的**：TrailView 出证任务 sessionStorage 续接+证书卡
   localStorage 持久化（TrailView.vue:24-56），且"绝不重跑已提交的出证"语义明确
   （:59 注释+resumeJobs 只轮询不重启）；FlightView 重挂靠以 `/telemetry/state`
   服务器事实为准（:632-659，"服务器是唯一事实源"）；旧 A-P0-1（/prove 前缀）
   实锤已修（TrailView.vue:183、:249 均 `/prove/case/`），旧 A-P0-2 的
   fzLastCaseId 已入身份域清扫清单（material.ts:65，ChainView.vue:100-126 读法
   正确）。
5. **同站 Cookie 对齐是提前排雷**：`alignSameSite` 把环回 API 基址与页面主机对齐
   （api.ts:31-41）——localhost 页面 + 127.0.0.1 API 的 SameSite 跨站丢 Cookie
   是这类会话改造最常见的翻车点，这里在客户端层一次治住并写了为什么。
6. **账户切换清扫单一事实源**：登录时 prev→new 不同即清身份域+会话域

7. **粒子克制且纪律干净**：prefers-reduced-motion 直接不出场（ParticleField.vue:
   25-26）、canvas aria-hidden、种子化 LCG 并注释"CSPRNG 红线不适用（视觉噪声）"

## 三、问题清单

> 级别：P0=演示翻车/宣称断裂；P1=明显缺陷；P2=打磨项。每条挂 文件:行号 或实测步骤。

### P0

**A-P0-1 审计收件箱全线死线索——旗舰双控动线在 live 栈 UI 走不通**
- 证据（实测 2026-09-30）：登录 auditor → 收件箱 20 条待立案线索 → **逐条点选
  立案 20/20 全部被拒**：`✕ warrant_target_unknown 目标授权编号 #137 不存在
  （无此授权记录）`（#134/#114/#108/#106/#103/#102/#93/#56/#53/#49/#48/#47/#40/
  #39/#36/#35/#34/#29/#28 同因）。根因（对照代码）：`/audit/violations` 从
  chain_events（event_type=1）聚合（backend/app/audit/router.py:244-262，链史
  保留 53 个 auth），而 create_warrant 校验 AuthRecord 表（audit/service.py:82-95，
  auth_records 现仅存 13 个可对上的 auth）——只读对账：`chain 违规 auth 53 个，
  可立案仅 13 个，死线索 40 个`；且 violations 按 last_at 倒序取前 20（router.py:
  284-289），**最新的 20 条恰好全是死线索**。UI 又把案号/目标做成只读
  （AuditView.vue:299-300），审计员无任何自救手段。
- 影响：审计台重设计的核心卖点"点选线索→自动立案→协同请求→批准"在当前演示
  数据态下第一步就断；评委随手点第一张卡即见报错。与上轮"判决件 404"同性质：
  API 各自为绿，聚合面无人验证。
- 修复方向：violations 聚合时 LEFT JOIN AuthRecord（无记录的线索降权/标注
  "原始授权记录已不在档——不可自动立案"或直接过滤），或 create_warrant 拒绝时
  UI 提供改填目标/降级为匿名令状（target_auth_id=null 路径后端本就支持，
  service.py:81）的出路；另补一条"收件箱线索可立案率"的浏览器级回归。

### P1

**A-P1-1 半途注册=永久孤儿账户，且 UI 无任何自救路（实测坐实）**
- 证据（实测）：注册向导第①步建户成功（服务端 accounts.status=pending_profile）
  后刷新/关页/切页——`pending` 仅存模块内存（auth.ts:98），丢失后重登该账户：
  prelogin 返回 challenge 放行登录（service.py:163-164），落地 /record 只见
  "尚无凭证——请从入口页登记"（RecordView.vue:189，实测截图
  s4b_pilot_deadend.png）；但入口页注册 tab 走同用户名→`username_taken`
  （实测），补资料向导只在 pending 内存态才可达。DB 里躺着的 revb-pilot
  （团队自己的更早测试）证明这个坑已被踩过。设计稿 §5 给管理员的"账户重置"
  能力在 AdminView 只有只读总览（:282-292），无处置动作。
- 影响：任何用户在两步向导间被打断（刷新/误点/断网）即产生一个**永远无法完成
  登记、也无法释放用户名**的账户；"换设备登录自动恢复"的宣称只覆盖已完成者。
- 修复方向：登录后若 me().status==="pending_profile"，RecordView（或门户）给出
  "继续补资料"入口复用第②步表单（/auth/profile 后端本就接受 pending_profile/
  active 双态，service.py:350）；或注册第①步落 sessionStorage 快照续接。

**A-P1-2 批准=不可逆解锁实名，却无任何确认闸**
- 证据：AdminView.vue:91-108 `approve()` 单击即签名+提交，后端批准即后台自动
  出函+解锁（collab.py:151-186），状态越过 pending 后不可逆（结案/驳回才终态）。
  按钮"批准（签名后自动执行解锁）"（:219）无二次确认、无输案号/勾选类防误触。
  对比：驳回反而有"理由必填"一道闸（:112）。
- 影响：双控体系的全部仪式感集中在"审慎批准"，而 UI 上它是与"重试执行"同权重
  的一击即发按钮；演示手滑或误触即解锁一名当事人实名，不可撤。
- 修复方向：批准加一道轻确认（卡片内展开"确认批准：将解锁实名 X，输入案号后
  四位"级），或至少 confirm 浮层复用 AuditView 的 modal 样式（:357 已有现成件）。

**A-P1-3 驳回理由是全页共享单 ref——跨卡串理由**
- 证据：AdminView.vue:89 `const rejectReason = ref("")` 被所有待批卡共用
  （:230 textarea、:112/:116/:123 读写）。在 A 卡输入理由→点 B 卡"驳回"→B 卡
  textarea 预填 A 卡文字，直接确认即把 A 的理由安给 B。收起再展开文本也残留
  （代码语义确定；live 走查因 A-P0-1 死线索未能走双卡对比）。
- 修复方向：`rejecting` 已按请求 id 记录（:88），rejectReason 应改
  `Record<id, string>` 或在 `rejecting` 切换/提交后清空。

**A-P1-4 审计台步进器样式漏共享化——四拍主隐喻渲染为裸文本**
- 证据：AuditView.vue:217-223 使用 `.stepper/.step/.step-n/.step-t/.step-arrow`
  标记，但其 scoped 样式未定义；样式只存在于 FlightView.vue:916-923（scoped 不
  跨组件）；ui.css 共享批（:105-153 注释"单一定义处，禁各视图手抄分叉"）恰恰
  没收编 stepper。实测截图 s5_audit_step0.png：步进器呈左对齐纯文本
  "1违规收件箱→ 2立案→…"竖排，与设计稿/飞行屏样式相去甚远。
- 修复方向：把 FlightView 的 .stepper 系上移 ui.css（共享批自钉的纪律补完一半），
  AuditView/ApplyView 复用。

**A-P1-5 TrailView 出证等待标签把 `{{ windowSel }}` 字面渲染**
- 证据：TrailView.vue:337 `:label="`TRAIL 出证中（窗口 {{ windowSel }} · 128
  样本，本机约 1 分钟）…`"`——v-bind 表达式内的 `{{ }}` 是 JS 模板串字面量，
  Vue 不做插值。出证全程（实测口径约 60-78s）状态标签恒显示"窗口 {{ windowSel }}"。
- 修复方向：改为 `` :label="`TRAIL 出证中（窗口 ${windowSel} · 128 样本…`" ``。

**A-P1-6 机构台"新请求不自动出现"——轮询闸门条件性失明（双控合流点）**
- 证据：AdminView.vue:59-67 轮询闸 `pending.value.some((x) => x.status ===
  "approved")`——只在"已有在执行件"时才拉取；审计员新发的 pending 请求不在
  触发集内，refresh 仅挂载与本页动作后执行（:46-53），页面也无手动刷新钮。
  实测注记：当前栈因存在 3 个僵尸 approved（见 A-P1-7）意外保活轮询而掩盖此
  缺陷；干净部署下"审计发函→切到机构台"永远看到"暂无待批请求"，演示必须靠
  F5。镜像问题：审计台轮询闸为 pending||approved（AuditView.vue:74），新违规
  线索进入同样不自动现身（KPI"未立案线索"静置不更新）。
- 修复方向：两台轮询改为无条件低频（如 10s）或以 total/updatedAt 增量探测；
  至少给两台各加一个手动刷新钮兜底演示。

**A-P1-7 approved 僵尸态无恢复——UI 无限期谎报"自动执行进行中"**
- 证据（live）：机构台 KPI"执行中=3"，三张卡（DSC-snp-162/DSC-approve-t1/B55，
  decided_ts 2026-09-27 与 09-29）至今显示"系统自动出函与解锁进行中——完成后
  状态自动流转…"（AdminView.vue:207）；collab.py 的执行线程在内存
  （_executing/_spawn_execute，:217-224），栈重启即失联，无任何启动扫描把
  approved 重投（main.py 无 recovery；collab.py 全文无 recover）。轮询闸又以
  approved 为条件（A-P1-6）——僵尸同时造成 4s 轮询永不停。
- 影响：状态机四拍宣称"已批准·待执行→已执行"自动流转，真实世界存在第四态
  "永远待执行"；评委若问"这单挂了两天了"即宣称断裂。
- 修复方向：启动时/定时把超时 approved（如 >5 分钟）重投 _spawn_execute 或落
  execute_failed（带"服务重启中断"人话）；UI 对超时 approved 显示"疑似中断——
  可重试"。

**A-P1-8 案卷既成后无"发起协同请求"的回路——令状孤儿**
- 证据：协同请求只能从第③步发起，而 createdWh 只存"最近一次立案"的哈希
  （AuditView.vue:131、:155）；立案后若切页/刷新（组件态全丢），历史案卷卡
  （:249-260）只有展示无动作，收件箱 unfiled=1 过滤后该线索也不再出现
  （router.py:289）。该令状永远无法再发函。
- 修复方向：历史案卷卡补"发起协同请求"动作（未解锁且无在途请求时），复用
  第③步表单按 wh 注入。

**A-P1-9 "每一步签名可追责"宣称超产（立案/结案/重试/吊销均未签名）**
- 证据：机构台横幅宣称"每一步签名可追责"（AdminView.vue:173）、台账区宣称
  "发函/批准/执行全程带签名指纹——每一步可追责到人"（:243）；实际：立案
  POST /audit/warrants 无签名字段（AuditView.vue:113-121；audit/router.py:307
  无 sig 校验）、结案无签名（collab.py:203-214）、重试无签名（collab.py:187-201）、
  吊销无签名（AdminView.vue:147-163）。AuditView.vue:9 头注"敏感操作（立案/
  发函/结案）以审计员钥签名"同超产（三者仅发函签名）。另有措辞称批准人将看到
  "目标与范围"（AuditView.vue:318）——系统不存在"范围"字段（ReqView 无此域，
  设计稿 §4 的"范围/时效进 AAD"未实现），机构台亦无处显示。
- 影响：这正是前两轮钉死的"宣称-实现-界面三点一线"问题在新层复发；评委对照
  设计稿问"范围在哪、立案签名在哪"即失分。
- 修复方向：最小改文案（横幅改"发函与批准双签留痕"、步骤③文案去掉"范围"）；
  正道是给立案/结案/吊销补签名（后端骨架已备 _verify_action_sig，collab.py:55-59）。

**A-P1-10 吊销：不可逆破坏性操作零确认、零签名、手填用户名**
- 证据：AdminView.vue:277-280 输入框+按钮直发 `/ra/revoke/by-username`
  （:147-163），无确认、无签名、无下拉选择（账户总览就在下方却不可点选）；
  手滑输错用户名=该用户全部有效凭证即时吊销（级联推链）。
- 修复方向：确认浮层+从账户总览行内"吊销"带名+操作入签名台账（顺带修 A-P1-9）。

### P2

**A-P2-1 结案浮层失败态伪装成"加载中"**：openTrace 失败 `trace=null`
（AuditView.vue:177-179），模板 v-else 统一显示"追溯数据加载中…"（:365-366）——
失败后永久"加载中"。改：区分 null（加载中）与 error（失败+重试钮）。

**A-P2-2 三态合一为"0"**：数据未到/为空/401 三种情形在两台均渲染为 0+"暂无"；
AdminView.vue:51 注释"401 由守卫层处理"不实——守卫只读 localStorage 旗标
（router.ts:33-42），会话过期后页面终身"暂无待批请求"而无提示/跳转。改：加载
骨架或"加载失败/会话过期，请重新登录"态。

**A-P2-3 案号只读且序号全局递增**：`seq=warrants.length+1`（AuditView.vue:99）
含历史全部令状，案号如 CASE-20260930-040（当日第 1 单也编 040）；后端拒绝重复
案号时 UI 无改号出路（案号 dd 只读）。改：当日计数或允许编辑案号。

## 四、设计层深问（超出单点修复的取舍）

1. **收件箱的数据契约问题**：chain_events 与 auth_records 是两个生命周期不同步
   的账本（链史永存、授权记录滚动），"违规→立案"的产品语义要求一个**权威 join
   视图**。现在 join 缺位（A-P0-1），明天就算过滤了死线索，"授权记录被滚除后
   违规史还追责吗"仍是开放问题——建议把"立案可用性"作为 violations 的一等字段
   （fileable: true/false + reason），UI 分区展示"可立案/仅存档"，把数据态诚实
   产品化，反而成为叙事点。
2. **双控的"范围"缺位**：设计稿 §4 的核心升格是"范围/时效进 AAD，超范围即验签
   失败"，实现里签的是 `REQ|wh|note`（collab.py:47-48、:92、:173）——范围/时效
   既不在签名里也不在 UI 里。当前"单令状单请求"客观上限定了范围，但宣称要么
   补实现、要么降格为"一函一令状"口径。这是 B/C 席更该追问的题，前端要先回答
   "批准人界面上到底在批准什么"。
3. **不可逆操作的分级交互**：系统里三类按钮风险迥异——发函（可驳回）、批准
   （不可逆解锁）、吊销（不可逆销证）——当前交互权重几乎相同（同一颗 .btn）。
   建议立一条交互纪律：不可逆操作一律过确认浮层+显示操作后果一句话；这比
   "大气感"更能体现司法产品的严肃性。
4. **门户与工作台的会话真相源**：本地 fzSession 旗标只做展示没问题，但页面内
   数据层把 401 静默吞成空态（A-P2-2）后，"会话已死"在 UI 上不可见。建议 api()
   对 401 统一广播一个事件（清旗标+回门户+人话提示），否则"为什么全是 0"会成
   演示日的暗雷。
5. **KPI 横幅的语义密度**：三台横幅好看，但机构台五数里"执行中"实为"已批准·
   执行中（含僵尸）"，审计台"未立案线索"含不可立案死线索——数字都"真"但都
   未经数据态校准。指标先定义清楚"可行动的待办"，再上横幅。

## 五、一句话结论

三台的**语义骨架与诚实姿态是三代交付里最好的一版**，但 live 实测把"最后一公里"
打回原形：收件箱 20/20 死线索让旗舰双控动线当场趴窝，步进器裸奔、批准无闸、
僵尸 approved 永久"进行中"——建议按 A-P0-1 → A-P1-1/2/6/7 → 文案宣称批的顺序
处置，清完这批，这层才配得上它下面的密码内核。
