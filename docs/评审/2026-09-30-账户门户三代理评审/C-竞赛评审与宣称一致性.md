## 一、总评

**档位判断：新账户层延续了"负例一等公民+判决行文化"的水准，宣称-实现纪律在账户层自身保持住了——但本批交付引入了两个"现场一试即穿"的宣称反例（E12 刷新重解锁、实弹脚本不可重跑），且评委第一读物（作品说明文档）整体停在账户批之前。**

前任 C 席（2026-09-28）定调："密码内核扎实，最后一公里的宣称收尾是最大风险；负例体系与真实组件零替身是最强差异化信号。"本轮检验结论分三句：

1. **延续住了的部分（多数）**：D 区负例表扩到账户面且全部实测复现——`pytest tests/ -q` 实跑 **269 passed, 0 failed（8 分 49 秒，exit 0）**；`e2e_browser_ui.py` 实跑 **29 项断言全绿（34 秒）**，与口径卡 D10 的"29"逐位一致；`e2e_roles_live.py` 实弹 A-E 段 30+ 项全绿（审计立案→双签→批准→执行→结案→驳回→重试全链路，含坏签名 401/空理由 422/越权 403/重复结案 409）。旧硬伤四项（超限事件 UI 断链/封链第二架次/协作函不绑令状/回执页守卫）**全数真修复**，且修复处带根因注释——这不是应付整改的样子货。
2. **跑在实现前面的部分（新病灶，两处）**：口径卡 E12 宣称"刷新后敏感操作需重输密码、明文私钥只在内存"——实现是 `cacheSk` 把**明文私钥写进 sessionStorage**（keystore.ts:335-340，代码注释自认"C 队长实测修复：sessionStorage 同步缓存"），F5 后不重解锁，30 秒可现场证伪；设计方案 §4 宣称"服务器自身被完全攻陷的场景下没有两把钥也无法合法完成解锁"——出函（FZC2 seal）与解封（unwrap）都是**服务端 kms 域钥动作**，服务器被攻陷即可绕过双签。这两处恰是前任警告的"宣称再次跑在实现前面"。
3. **演示资产可重复性（新短板）**：`e2e_roles_live.py` 第二次起必在 F.1 挂 500（测试播种占位公钥与历史撤销集 UNIQUE 冲突→未捕获 IntegrityError）；协作请求状态机存在**无恢复路径的孤岛态**（当前机构台挂着 3 张 09-29 的"已批准·待执行"僵尸卡，retry 只认 execute_failed）；演示库内测试残留显著（11+ 测试案卷、14 条协作请求、7+ 测试用户）。

定性：**内核与负例体系仍是第一梯队上游；新层工程质量高于上一轮平均；"可重复的演示资产"与"评委可见文档的三点一线"是答辩前必须收尾的两件事。**

## 二、得分点（按对评委冲击力排序，挂证据）

1. **双控从流程约束升格为密码学强制——且负例可现场打**。请求哈希 `req_hash = SM3("FZ-COLLAB-REQ|v1|"+令状哈希+"|"+理由)`（backend/app/accounts/collab.py:47-48），审计员钥与管理员钥对**同一消息**各自 SM2 签名（collab.py:92 发函、collab.py:173 批准）；批准内容被篡改=验签失败有专门负例（tests/test_collab_dual_control.py:175-183，`note` 换串→401 bad_sig，今日实弹复现）；FZC2 信封 AAD 绑定 `(凭证哈希‖令状哈希)`（backend/app/ra/collab.py:107-115）+ scope_mismatch 403（audit/router.py:399-408）——三模块评审 F-③⑤"一函多令状/无一致性校验"硬伤根修完成。答辩话术"缺一不解锁、挪用即验签失败"有逐条可复现的实弹。

## 五、演示剧本建议（三角色双控主线，8 分钟骨架）

**前提整备（答辩前一晚）**：demo_down→清库→demo_up（真链档）→`seed_accounts.py --auditor-pw … --admin-pw …`（固定演示密码，现场不猜）→**预飞一条"今天"的飞手动线**：注册飞手（两步向导本身就是演示点）→起飞申请（65-90s 等待期讲撤销电路+自研 SNARK）→取令牌→ARM→冲围栏→固件拦截→封链。这条预飞行同时完成三件事：给审计台产出"今天"的违规线索、给收件箱动线备料、验证链/SITL 在线。

- **0:00-0:40 门户**：登录页讲"服务器不存口令不存哈希，认证=SM2 挑战-应答"；负例一手：错密码→"密码错误（密封件解封失败）"，F12 Network 面板显示**无验证请求发出**（本地 AEAD 判）——30 秒打出零口令存储。
- **0:40-2:30 审计台立案**：切审计员（首登激活话术一句带过）→KPI 带→点违规卡片自动立案（案号/目标/依据模板自动带出）→确认立案（哈希+原文双锚上链）。
- **2:30-3:30 发函**：解锁审计员密钥（输密码——讲"私钥只在内存"前先确认与 E12 口径收敛一致，见问题 2）→签名发起→原地状态卡"待批准"。
- **3:30-4:30 机构台批准**：切 admin→卡片展示依据原文/理由/目标/发函人指纹（"明白为什么"的实物载体）→批准即返回"已批准——自动执行进行中"。
- **4:30-5:30 切回审计台看流转**：5 秒轮询自动跳"已批准·待执行→已执行·待结案"（这段等待正好口播双签绑定语义："两把独立钥匙签同一请求哈希，缺一不解锁，挪用即验签失败"）→查看实名并结案→已结案（金色徽章）。
- **5:30-7:00 回飞手侧收尾**：链上留痕面板看这次令状/事件/解锁留痕，或 TRAIL 证书 verify-instances 现场实跑（前任剧本保留）。
- **负例插播位（各 20 秒）**：空理由发函 422/审计员直打机构 URL 弹回/同案号重复立案 400。
- **兜底纪律**：①**不现场跑 e2e_roles_live**（问题 1 未修前必挂 F.1）；②每个现场环节备 60 秒录屏；③若批准后真出 execute_failed（如误对历史纪元凭证立案），不要慌——人话失败原因+重试按钮本身就是"结构化诚实"加分项，但对主线务必用当日新鲜数据。

**空态预案**：万一收件箱空（清库后忘了预飞），UI 空态文案自带"让飞手飞越围栏触发取证"指引（AuditView:244），照做即可，动线约 3 分钟。

## 六、一句话结论

**这是一个把上一轮"最后一公里"警告听进去了的批次——账户层的负例、测试与文档三点一线做得比上一轮平均水准更好；但现在最锋利的两把自伤刀是"口径卡 E12 与 sessionStorage 现实相反"和"实弹脚本第二次必 500"，加上评委第一读物（作品说明文档）还停在账户批之前——把这三件事在答辩前收掉，这一批就是净加分；收不掉，它们恰好落在评委最容易伸手摸的位置上。**
