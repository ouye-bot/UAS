**冲突/错误发现（按严重度排列）：**

### F1【事实错误·重写前必须修正】S7 的 RFC 编号错误，且引注不实
- 校准报告 S7 称：SM2-OPAQUE 标注"RFC 9380 框架的国密实例"（**行 144 已有此表述**，前端测试已锚 RFC 9380 K.1 官方向量）。
- 实测：`grep -c "9380"` 正文 = **0**；正文行 144 原文为"**OPAQUE 协议框架的国密实例**"与"**非 RFC 9807 全义实现**"，并无 RFC 9380 字样。
- 外部核实（rfc-editor.org/info/rfc9380）：**RFC 9380 =《Hashing to Elliptic Curves》**（IRTF/CFRG），并非 OPAQUE；OPAQUE 协议的 RFC 为 **RFC 9807**（rfc-editor.org/info/rfc9807）。正文行 144 现有表述正确。
- 错误源头：`uas/docs/性能档案.md:21/25` 的"RFC 9380 K.1 官方向量"（K.1 测试向量附录属 RFC 9807，系 9807 笔误），校准报告未核对即转抄。
- 危害：照 S7 执行会把错误编号写入终稿，违反写作合同"零虚假捏造""术语用官方权威表述"。
- 处置：S7 改为"RFC 9807（OPAQUE）框架的国密实例"，并同步订正性能档案.md 行 21/25。

### F2【计数错误·必须修正】S3 的表 1 角色计数"飞手 10 项"错误
- 表 1（正文行 40~46）飞手实际 **7 项**；校准报告所列 10+5+3+2+3=23，与其自称的"20 项功能"自相矛盾（总数 20 正确：7+5+3+2+3=20）。
- 处置：更正为"飞手 7 / 机构管理员 5 / 审计员 3 / 机构 2 / 系统级 3"。S3 数字总起句方案本身不受影响。

### F3【数字未复算·建议订正】去年模板字数类数字与"表 4=26 行"
- 本次按校准报告 §0 自述方法复算去年模板：全文非空白 **14,685** 字（报告 14,421）；第 3 章 **7,835 字 = 53.4%**（报告 7,662/55.7%）；第 4 章 **639 = 4.4%**（报告 632/4.6%）；第 5 章 **433 = 2.9%**（报告 428/3.1%）；去年表 4 实为 **23 个用例行 × 5 列**（含表头 24 行；报告在 S9、主线二、highlights#4 三处写"26 行×5 列"）。
- 影响评估：方向与结论不变（第 3 章仍是证据主体、约占一半；我方 20.9% 的差距真实存在）；S9 新表明标"约 20~26 行"不受影响。但报告尾注称"全部复核命令与计数见第 0 节"，而 §0 明言仅我方基线为本次复算——去年字数系转抄结构分析、未经复算，宜统一复算后更正或明确标注"转抄"。
- 另：§0 称"正文 387 行"，实测 **386 行**（wc -l 与 Python splitlines 一致）。

### F4【与写作合同的字面冲突·需补豁免注记】S6 取消 2.2"运行结果"独立节
- 写作标准·三 明文："模板=……2 设计与实现方案（**实现原理/运行结果/技术指标**）→3 系统测试与结果"，且"违反任何一条即评审不通过"。S6 将运行结果整体迁入第 3 章，与合同括号注记字面相抵。

- 处置：在校准报告 deviations#2 或合同补一句显式豁免，援引"一二级标题可增删"条款，避免评审代理按字面判违规。
